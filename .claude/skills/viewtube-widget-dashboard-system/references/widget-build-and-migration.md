# Widget build and migration

For a new widget define: name/ID, creator job, purpose, inputs, outputs, data/dependencies, primary action, central functional component, archetype, permitted primitives, custom compound component, primary palette, justified color pops, default/min/max W/H, pages, desktop/narrow/mobile compositions, interaction/data states, accessibility, screenshots and certification.

Prefer a unique functional interior built from shared primitives. Custom domain components are first-class when they make the tool recognizable or usable; preserve Comment Responder/Goals Tracker-like specialization and normalize only shared geometry/style/state contracts.

Migration sequence: inventory -> screenshot baseline -> primitive map -> token/color migration -> layout/height -> responsive/mobile -> data states -> actions -> accessibility -> CSS cleanup -> W x H fixtures -> screenshots -> certification. Do not rewrite working widgets merely for visual uniformity.
