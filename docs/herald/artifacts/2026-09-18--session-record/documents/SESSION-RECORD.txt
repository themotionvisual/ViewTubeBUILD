 3. BUGS I INTRODUCED AND CAUGHT
================================================================================

 Worth recording because the pattern repeats: each was found by testing or
 re-reading, not by being careful the first time.

 a) promote moved VERSIONS.md into variants/ — it demoted the record of the
    choice. Cause: "which files are artifacts" decided ad-hoc in 3 places.
    Fixed with one shared definition, not a patch to one call site.

 b) Ledger recorded renames as the literal string "old -> new" instead of a
    path. Fixed by parsing NUL-delimited git output.

 c) The git helper called .trim(), which ate the leading status space of the
    FIRST porcelain record and shifted its path by one character. So the first
    changed file was always recorded wrong.

 d) Editor_V1 and Editor_V3 did not group, because \b fails before V when
    preceded by "_" (a word character) — exactly how those files are named.

 e) Editor_V1 then beat Editor_V3 as canonical, because equal sizes fell
    through to mtime. Version numbers now outrank size.

 f) My own lean cut re-optionalised the repo-recommendation block, silently
    undoing the fix from four turns earlier. Caught by reading the contract
    back to you. The lean rule now records that block as its one permanent
    exception, WITH THE REASON.

 g) check:cost rejected my own one-page overview at 2,520 vs 2,500 tokens.
    Trimmed instead of raising the budget.

 5. THE TEMPLATE AS IT STANDS
================================================================================

 ALWAYS
   TASK        one sentence, your words
   DONE WHEN   the observable result · checked by: <command>
   ALREADY?    new | partly done <where> | already exists <where> | tried before
   FILES       exact paths to create / edit / delete
   PLAN        1. … 2. … 3. …
   NET         +lines / -lines  (adding only? say what you considered removing)

 ONLY WHEN THE TRIGGER IS TRUE — one line, no heading, omitted otherwise
   better idea · tools · docs · branches · reduce · risk · prototype · owner ·
   tests · rollback · cost · skill · task id · saved · retire · unfinished

 PLAN FILES
   required: goal · done when · steps (checkboxes) · before -> after · status
   optional: prior work · references · decisions · risks · reduction · follow-ups

 RULES
   1. A section appears only if it changes what you do next. No "N/A" padding.
   2. Prefer removing code to adding it. Shared component before a new one.
   3. Quarantine before deleting. Record how to restore.
   4. Separate what was RUN and OBSERVED from what is merely believed.
   5. Link to files; never paste them into the conversation.
   6. A prototype or demo proves nothing about what actually runs.

 EVIDENCE LADDER
   PROVEN   runtime/test · canonical main code · git history
   CLAIMED  user correction · task index · active branch · artifact
   UNKNOWN  conversation · memory
   A task never reaches "Finished" below PROVEN.

 PROPOSING A SECTION
   node scripts/agent-template.mjs propose --new   -> fill in the shape
   npm run template:pending                        -> what awaits approval
   node scripts/agent-template.mjs approve <id>    -> your call
   A proposal needs a "why" naming a CONCRETE OBSERVED FAILURE, not a hunch.
   Rejections keep their record so the idea is not re-proposed.
