1. Purpose
ViewTube has accumulated many standalone HTML prototypes because they were a fast way to develop exact compositions, 
component systems, dashboards, data tables, Kanbans, animation references, and promo captures. The inventory exists so useful 
work is not lost and duplicate experiments do not remain indefinitely indistinguishable from production.
2. Canonical Prototype Record
Every standalone HTML record should include:
 filename;
 category;
 short purpose / what it demonstrates;
 source path / Library reference;
 screenshot/preview;
 related Task Index IDs;
 related production component/route;
 real-data vs mock-data status;
 interaction status on desktop/mobile;
 productionized? yes / partial / no;
 disposition: PROMOTE / MERGE / REFERENCE / SUPERSEDED / ARCHIVE;
 strongest/canonical version if duplicates exist;
 notes.

4. Disposition Vocabulary
PROMOTE
The prototype is the strongest implementation of a capability and should be ported into the production React/TypeScript 
architecture.
MERGE
The full prototype should not become a product route, but specific interactions, compositions, controls, or algorithms should be 
extracted into the canonical implementation.
REFERENCE
The file remains valuable as a design/behavior/source reference, but production owns a separate implementation.
SUPERSEDED
A stronger successor exists. Preserve screenshot/provenance and then archive the earlier version.
ARCHIVE
The file has no remaining unique implementation value after documentation and may be moved out of active working/reference 
directories.
5. Prototype-to-Production Gate
A standalone HTML should not be called productionized merely because a similar-looking React component exists. Certification 
should verify:
1. the unique interaction/visual idea was actually ported;
2. real data or the intended service is connected;
3. state persists correctly;
4. mobile behavior works;
5. help/entitlement/provenance behavior matches the production system;
6. the production component has an owner/registry ID;
7. the prototype has a recorded replacement.
6. Known High-Value Prototype Families
Consolidation / governance trackers
Keep the strongest tracker versions because they contain the historical architecture decisions, status language, resource 
badges/code snippets, and migration thinking that explain why current architecture exists.
Component libraries
Do not treat the component-library HTML files as runnable product pages. Mine them for canonical ViewTube controls, Vault 
modules, icon/header treatments, micro compositions, and interaction patterns. Deduplicate sibling files only after a strongest 
version is chosen.

Analytics / data-table prototypes
Use them to recover precise table/visual composition and interaction, then connect the production version to VT-SYNC. Mock-data 
prototypes remain reference sources, not analytics data owners.
Projects / Kanban prototypes
The early content-planning Kanban is superseded by stronger flagship/integrated versions. Preserve the strongest 
drag/tap/workspace/autosave behaviors while converging on the one canonical Project model.
Promo capture HTML
Promo standalone files are intentional derivatives. Their purpose is deterministic 16:9 capture, not route ownership. They should be
linked to the canonical visual and kept in a predictable capture/reference folder.

8. HTML Catalog / Index Requirements
The permanent catalog should allow search/filter by:
 filename/title;
 category;
 status/disposition;
 productionized state;
 related route/tool/visual;
 Task Index IDs;
 data type;
 mobile status;
 source/capture/reference.
It should include a preview/screenshot link where possible.
9. Duplicate Detection Rules
Near-duplicate HTML prototypes should be compared by:
 DOM structure;
 visible composition;
 interaction features;
 state/persistence behavior;
 mock-data contracts;
 modification chronology;
 production linkage.
Mark one strongest/canonical reference before archiving the rest.
