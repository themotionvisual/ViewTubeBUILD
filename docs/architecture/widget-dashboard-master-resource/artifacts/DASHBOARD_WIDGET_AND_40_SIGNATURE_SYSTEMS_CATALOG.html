1. Dashboard Architecture

The dashboard is a configurable command surface built from a canonical Widget Registry and persisted layout state. A widget definition should declare:

  • stable widget ID;
  • category and renderer;
  • release tier/status;
  • data/API dependencies;
  • default visibility/order;
  • supported size and height pairs;
  • logged-out behavior;
  • persistence contract;
  • entitlement requirements;
  • mobile behavior;
  • help copy;
  • certification state.

Shell color is layout/position styling; metric/chart colors remain semantic and must not change meaning merely because a widget is moved.

5. Widget Certification Queue

A prototype or preview widget should be individually promoted, not exposed en masse.

Certification criteria:

  1. 1. useful and non-duplicative;
  2. 2. clear data availability;
  3. 3. production renderer selected;
  4. 4. logged-in and logged-out states defined;
  5. 5. no silent sample fallback;
  6. 6. desktop and mobile layout valid;
  7. 7. performance cost acceptable;
  8. 8. help/provenance copy present;
  9. 9. persistence and entitlement behavior defined;
  10. 10. registry metadata complete;
  11. 11. runtime error/empty/loading states tested.

Rejected/duplicate concepts are archived with a reason so they are not rediscovered repeatedly.

6. Logged-In / Logged-Out Population Rules

Logged in

Default to real connected data or explicitly imported data. Do not swap in demo values simply to maintain visual density.

Logged out / disconnected

A widget that depends on Google/YouTube should show an intentional state such as:

  • requires_connection;
  • signed out;
  • connected but expired/invalid;
  • loading;
  • API error;
  • empty valid result.

Demo/sample

Sample/demo content may be offered when intentional, but it must be visibly labeled SAMPLE DATA and should not be indistinguishable from a real connected workspace.

9. How the 40 Relate to Widgets vs Super Tools

“Widget / Tool Systems” does not mean every idea should become a dashboard card.

Use the appropriate form:

  • Dashboard widget - compact at-a-glance state/action.
  • Toolbox/subtoolbox - focused workflow within Studio.
  • Full super tool - multi-step workspace that creates artifacts/handoffs.
  • Brain action/engine - background/ranked analysis surfaced through another UI.
  • Process row - progress/checklist across a known workflow.
  • Visual - data encoding rather than a tool workflow.

For example, Next Best Action may have a compact dashboard widget plus a deeper command-center tool; Creator Canvas OS should remain a full workflow, not be squeezed into a tiny card.

10. Signature-System Handoff Principle

Every promoted signature system should reuse:

  • canonical channel/video/project/asset IDs;
  • VT-SYNC selectors where analytics are needed;
  • universal action/output packets;
  • automatic project/video context passing;
  • Brain evidence/provenance rules;
  • dashboard certification and Studio/toolbox architecture as appropriate.
